# 実装構成

`Program` が設定を読み、`RunnerService` がパッケージと実行ごとのディレクトリを管理します。`GitHubRunnerClient` は公式ランナーの取得・SHA-256 検証と GitHub API 操作、`MxcExecutor` は SDK のプロセスとパイプの寿命管理を担当します。

```text
Windows ホスト
  mxc-gh-runner run
    ├─ GitHub API: 公式リリース・登録トークン
    ├─ packages/: 検証済みランナーのテンプレート
    ├─ logs/: 標準出力・標準エラー
    └─ MXC ProcessContainer
         └─ mxc-gh-runner __worker
              ├─ Runner.Listener configure --ephemeral --disableupdate
              └─ Runner.Listener run
                   └─ GitHub Actions の 1 ジョブ
```

`__worker` と `__smoke` は CLI が起動する内部エントリーポイントです。通常は直接実行しません。

## 起動と後処理

1. JSON の未知・重複フィールド、リポジトリ URL、パス、値の範囲を検証します。
2. 公式 `actions/runner` のリリースとチェックサムを取得し、ZIP を検証して展開します。展開先を逸脱するアーカイブのエントリーは拒否します。
3. 使い回すテンプレートから、新しい GUID 名の実行ディレクトリへランナーをコピーします。
4. ホストのアクセストークンから登録トークンを作るか、指定された短期登録トークンを使用します。
5. 明示的に構築した環境変数・ファイル権限で MXC を起動し、登録情報を標準入力へ渡します。
6. MXC 内で `--ephemeral` と `--disableupdate` を指定して登録し、ランナーを起動します。
7. 標準出力・標準エラーを並行して読み、既知のトークンを伏せて転送します。時間切れや Ctrl+C ではプロセスツリーを停止します。
8. アクセストークンがある場合は残ったランナー登録の削除を試み、アプリケーション所有の GUID 名の作業領域を削除します。

初期版では、既存のパッケージキャッシュはリリース情報と実行ファイルの存在を確認して再利用します。ホスト上のキャッシュ自体は信頼する領域です。キャッシュを信頼できない場合は新しい `stateDirectory` を指定して取得し直してください。

## プレビューの制約

実行コンテナは Windows ホストの OS と読み取り許可されたツールを使用します。VM イメージ、完全に独立した OS、パッケージインストール済みのビルドイメージは作成しません。UI サブシステムを全面無効化するとこのホストの .NET 初期化に失敗するため、`Ui.Disable=false` を使用し、クリップボードと入力注入を個別に制限します。

ランナーは自分の作業パスの親ディレクトリを列挙して検証するため、ProcessContainer の `EnumeratePaths` で作業パスの親からドライブのルートまでを指定します。これはディレクトリ内の名前を列挙する許可です。親ツリー全体へのファイル内容の読み取り・書き込み許可は付与しません。この機能に対応しないバックエンドでは起動を失敗させます。

各実行領域のルートには `global.json` の `{}` と、空の `<Project />` を持つ `Directory.Build.props`・`Directory.Build.targets`・`Directory.Packages.props` を作成します。.NET SDK と MSBuild が親ディレクトリを探索した際にここで止まるため、ホストの設定ファイルを読もうとして権限エラーになったり、ホスト側のビルド設定を継承したりするのを防ぎます。SDK バージョンを固定する場合はワークフローのリポジトリ内に `global.json` を用意してください。ホストには指定した SDK のインストールが必要です。

書き込み可能な `stateDirectory` と、CLI・Windows・.NET・追加ツールの読み取り許可範囲は重ねません。どちらかが他方を包含する場合も設定エラーにします。`init` は設定ファイル隣の `.mxc-runner` をまず検証し、重なる場合は `%LOCALAPPDATA%\MxcGitHubRunner` を検証して選びます。両方とも許可範囲に重なる特殊なインストール構成では、ツールの外側へ `--config` を指定してください。

`doctor` の成功は MXC バックエンドの検出を表します。`.NET` とパイプ・作業領域の動作は `smoke`、ランナー登録とジョブ実行は実際のワークフローで確認する必要があります。ランナーの終了コードとワークフローの結論は別の値です。

SDK の確認には `dotnet --version` を使用します。このホストでは `dotnet --info` に含まれる追加のシステム情報取得が MXC の権限により失敗するため、ワークフロー例の確認項目に含めません。

GitHub 登録とジョブ実行に使う通信は外向きに許可しています。ワークフローは渡されたトークンや読み取り可能なデータを使用できるため、実行対象は利用者が承認したリポジトリとワークフローに限定してください。
